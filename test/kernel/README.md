# Integration VM kernel configuration

`aya_aarch64.config` and `aya_x86_64.config` are KCONFIG_ALLCONFIG request
fragments for the integration VM kernels declared in `MODULE.bazel`.
`linux.bzl` resolves each fragment from `allnoconfig` using the
integrity-pinned Linux source and the configured LLVM platform.

The fragments contain requested values, not complete Linux `.config` files.
Linux Kconfig adds defaults and values derived through dependencies, `select`,
and `imply`. Keep an assignment in a fragment when an integration VM requires
the value or when the assignment intentionally pins a Kconfig default. Do not
copy generated values from a resolved `.config` into a fragment.

The static rules resolve configurations during Bazel analysis. Declared
toolchain capabilities are checked with the selected tools before kernel
artifacts are produced. Probes without a declared answer use their
source-selected fallback and emit a warning. Those fallbacks can select
different options from native Kconfig using the actual compiler; a successful
kernel build does not establish configuration equality.

Both fragments build `sch_ingress.ko` as a loadable module. The VM initramfs
includes that module and an alias file generated by `test-distro:depmod`, so
the `modprobe` integration test exercises the kernel's usermode helper.

VM targets cover Linux 5.10, 5.15, 6.1, 6.6, 6.12, and 6.18 on both guest
architectures. Each VM runs the default and optimized Rust test binaries,
built with nightly for eBPF. Select stable userspace with the commands below.
Kernel patch versions and archive checksums are pinned in `MODULE.bazel`.
Each kernel line has one configured build in
`@aya_kernel_<line>//consumer`; its target platform selects the architecture.
The boot image, resolved configuration, symbol table, and ingress module are
selected from that same build. The package and VM target names stay the same
across patch updates.

`kernel.BUILD.bazel` defines the consumer package inside each generated
repository. Keeping it there avoids fetching every kernel when ordinary
`bazel test //...` discovers workspace packages.

## Generator pins

The `generator_<line>.json` manifests pin the repository generator separately
from the Linux source. Bazel downloads the generator for the repository host;
the same generator supports both guest architectures. It exports Kconfig and
Kbuild data for Bazel analysis. Bazel then compiles the selected kernel objects
with the configured LLVM toolchain.

Kernel C compilation uses separate Clang frontend and backend actions. The
backend can share cached objects when configurations produce identical
bitcode and backend inputs. This requires `bazel/rules_cc_ir.patch` and the
output path mapping settings in `.bazelrc`.

Keep the generator artifacts and the `linux.bzl` revision in `MODULE.bazel`
together: the generated rules load shared helpers from that module. Each
generator embeds a native Kconfig parser compiled from its kernel source.
Changing that parser or its support sources requires rebuilding the generator;
ordinary Kconfig and Makefile changes trigger repository generation again.
The generator checks the parser source digests before accepting a source tree.

## Remote builds

The commands below use Aya's remote BuildBuddy service, which requires an API
key. From the repository root, read the intentionally public CI credential and
set the arguments once in your current shell:

```console
$ aya_buildbuddy_key=$(awk '$1 == "BUILDBUDDY_API_KEY:" { print $2; exit }' .github/workflows/ci.yml)
$ aya_remote=(--config=remote
    --remote_header="x-buildbuddy-api-key=$aya_buildbuddy_key"
    --remote_downloader_header="x-buildbuddy-api-key=$aya_buildbuddy_key")
```

## Reproduce the resolved configurations

From the repository root, resolve both fragments with:

```console
$ for arch in aarch64 x86_64; do
    bazel build "${aya_remote[@]}" --lockfile_mode=error \
      --platforms=@rules_rs//rs/platforms:${arch}-unknown-linux-musl \
      @aya_kernel_6_18//consumer:kernel_config
  done
```

Use `bazel cquery "${aya_remote[@]}" --output=files` with the same platform and
label to print the generated `.config` path. Add
`--remote_download_outputs=all` to the build command to read it locally.

Compare both architectures with Linux's native Kconfig resolver using the
selected compiler and BTF encoder:

```console
$ bazel test "${aya_remote[@]}" --lockfile_mode=error \
    @aya_kernel_6_18//consumer:kernel_config_parity
```

After changing either fragment, rebuild both resolved configurations and run:

```console
$ bazel --host_jvm_args=-Xmx8g test "${aya_remote[@]}" --lockfile_mode=error \
    --@rules_rust//rust/toolchain/channel=stable \
    //test/integration-test:vm_aarch64_6_18 \
    //test/integration-test:vm_x86_64_6_18
```

Replace `6_18` with another kernel line, such as `5_10`, to run its tests.
The VM targets are manual and must be invoked explicitly.

## Run a VM on macOS

The local macOS VM target uses Homebrew QEMU. The kernel and test binaries
can still build remotely. Install QEMU and select its toolchain explicitly:

```console
$ brew install qemu
$ bazel --host_jvm_args=-Xmx4g test "${aya_remote[@]}" --lockfile_mode=error \
    --@rules_rust//rust/toolchain/channel=stable \
    --platforms=@platforms//host:host \
    --extra_toolchains=@homebrew_qemu//:x86_64 \
    //test/integration-test:vm_x86_64_5_10_macos
```

This x86_64 guest uses software emulation on ARM hosts.
